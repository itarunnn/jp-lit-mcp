01

まず、土台を分ける

Framework は何をして、
何をしていないか

この repo に「全部入りの web framework」はない。小さな部品を組み合わせ、MCP の通信部分と文献検索の業務ロジックを分離している。

A

Node.js 22+

プロセス、標準入出力、filesystem、組み込み fetch を提供する実行環境。HTTP server を公開するのではなく、MCP host の子プロセスとして動く。

runtime
B

MCP SDK

McpServer、tool 登録、schema 公開、StdioServerTransport を担当する。検索方法やデータの意味は知らない。

protocol framework
C

TypeScript + ESM

adapter 間の共通契約を型で固定する。NodeNext なので source 内の import もビルド後を見越して .js を付ける。

language & modules
D

Zod

LLMから届く未知の入力を runtime で検証し、MCP client に input/output schema を公開する。TypeScript の型だけでは守れない境界を守る。

runtime contract
E

Vitest

adapter、mapper、service、persistence、MCP manifest を fixture 中心に検証する。実APIの揺らぎと自分の変換ミスを切り分ける。

test runner
重要な境界

MCP SDK は「tool を呼べるようにする」。この repo は「どの source をどう検索し、何を共通形式で返すか」を実装する。

03

コードツアー

jp_lit_search
一回の旅

最も理解しやすい入口は、抽象的な class 図ではなく一つの呼び出しだ。ここでは文字列 "夏目漱石" が検索結果になるまでを追う。

  1. 1

    src/index.ts

    プロセスを起動する

    main() は CLI option を振り分け、通常時は startServer() を呼ぶ。ここは domain logic を持たない、実行ファイルの玄関。

  2. 2

    src/server.ts

    依存を一度だけ組み立てる

    createServer() が cache、session、clients、adapters、services、tools を生成する。これが composition root。最後に SDK の registerTool へ handler と Zod schema を渡す。

  3. 3

    src/tools/jpLitSearch.ts

    外部入力を tool の言葉へ変える

    searchInputSchema.parse(input) で検証し、cache 対象から force_refresh を除外する。Tool は MCP response の content と structuredContent も組み立てる。

  4. 4

    src/lib/persistence/runCachedTool.ts

    同じ問いなら結果を再利用する

    入力を正規化し hash key を作る。hit ならAPIへ行かず返す。ただし session entry は追記し、「今回その結果を使った」事実を残す。

  5. 5

    src/services/searchService.ts

    一つか、横断かを決める

    source 指定時は一 adapter。未指定時は複数 source を Promise.allSettled で並列検索し、成功分を round-robin で混ぜる。

  6. 6

    src/sources/ndlSearch/adapter.ts

    共通語を source 固有語へ翻訳する

    共通の SearchParams を CQL と SRU URL に変換する。response は parser / mapper を通し、共通 SearchItem に戻す。

  7. 7

    src/tools/jpLitSearch.ts

    LLMが扱える二重形式で返す

    人間にも読める JSON text と、client が型付きで扱える structured content を同時に返す。diagnostics と cache metadata もここで付く。

核心だけ抜き出す
const parsed = searchInputSchema.parse(input);

const result = await runCachedTool({
  input: cacheableInput,
  live: () => searchService.search(parsed)
});

return {
  content: [{ type: "text", text: JSON.stringify(response) }],
  structuredContent: response
};

境界：TypeScript の型注釈では、プロセス外から来た値は検証できない。Zod の parse が「未知の JSON」を信頼できる入力へ変える。

05

なぜ、この形か

コードに埋め込まれた
設計判断

↳

Factory function

createJpLitSearchTool(service, cache, sessions) のように必要物を引数で受ける。global singleton を避け、fixture や fake を差し替えやすい。

∥

Promise.allSettled

一つの外部APIが落ちても全検索を失敗させない。成功分を返し、失敗は安全な source_errors として可視化する。

≋

共通 interface

SourceAdapter は search と getRecord だけを要求する。service は NDL や CiNii の詳細を知らずに呼べる。

⇄

Round-robin merge

横断検索で最初の source だけが上位を独占しない。各 source の結果を順番に取り、発見経路の多様性を保つ。

◇

Mapper を分離

network I/O と data projection を分ける。保存 fixture だけで複雑な XML / JSON 正規化を高速に試験できる。

!

明示的な副作用

Tool annotations で external read、local write、destructive operation を client に伝える。「検索＝完全な read-only」ではない。

共通契約 — src/sources/types.ts

interface SourceAdapter {
  source: SourceName;
  search(params: SearchParams): Promise<SearchResult>;
  getRecord(sourceId: string): Promise<RecordItem | null>;
}

この小ささが重要。APIごとの高度な機能は dedicated tool / client に逃がし、全 source に無理な共通化を強制しない。

06

似ているが、違う

Cache と Session を
分けて考える

RESULT MEMORY

File Cache

「この入力の結果は何だったか」

  • tool名＋正規化入力から key を作る
  • 外部API呼び出しを再利用する
  • force_refresh で bypass できる
  • structured content を保存する
≠

RESEARCH MEMORY

Session Store

「調査で何を使い、どう判断したか」

  • cache hit でも entry を記録する
  • 選択項目、note、trace を保持する
  • 後で検索・注釈・export できる
  • 調査の再現性を支える
MISSnormalize → key → API → cache write → session append → return
HITnormalize → key → cache read ─────────→ session append → return

src/lib/persistence/runCachedTool.ts がこの二つを一か所で調停する。cache は性能だけでなく、同じ調査入力に安定した snapshot を与える役割も持つ。

07

理解を実装へ

新しい Source / Tool を
追加する道順

A

RECIPE

Source adapter を追加

  1. API契約を確認利用条件、rate limit、payload、identifier
  2. fixture を保存search / record の代表 response
  3. mapper を test-first で実装payload → SearchItem / RecordItem
  4. SourceAdapter を実装query構築、fetch、error変換
  5. server.ts で生成adapters 配列へ追加
  6. schema と docs を同期SourceName、tool description、利用条件
B

RECIPE

MCP tool を追加

  1. tool の境界を決める既存検索の option か、独立 use case か
  2. Zod input/output を定義src/lib/schemas.ts
  3. handler test を先に書くstructuredContent と副作用
  4. factory handler を実装src/tools/
  5. 依存を server から注入client / service / persistence
  6. SDKへ登録description、schema、annotations
追加前に一度止まる

source 固有の全文・画像・典拠検索を、無理に SourceAdapter へ詰め込まない。全 source に共通な「書誌検索・詳細取得」だけを adapter にし、特殊機能は dedicated client / tool として保つ。
